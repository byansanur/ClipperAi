# Backend Summary

This document summarizes the current state of the **ClipperAi Backend** after completing all post-MVP enhancements.

## 🎯 Achievements
The ClipperAi backend is now a robust, resource-aware automation engine. It can receive a YouTube URL, intelligently analyze the most engaging moments, and automatically generate short vertical clips (9:16 aspect ratio). The entire process runs completely on your local machine with built-in safeguards against resource starvation and redundant processing.

## 🛠 Tech Stack & Tools
- **Language**: Go 1.21+
- **Web Framework**: Gin HTTP
- **AI/LLM**: Ollama (Running locally, default model: `llama3.2`)
- **Media Processing**: FFmpeg & yt-dlp
- **Configuration**: `godotenv` (.env file)
- **Concurrency**: Buffered Channel Semaphore (capacity: 1)

## ✨ Key Features Implemented

1. **Asynchronous API (Polling, Cancellation & Generate More)**
   - `POST /api/v1/clips`: Accepts a video URL, generates a Job ID (UUID), and immediately returns an HTTP 202 Accepted response. If the same URL and layout were already processed, returns HTTP 200 with cached data.
   - `GET /api/v1/clips/:id`: Allows the client to check the job status (`processing`, `completed`, `failed`).
   - `DELETE /api/v1/clips/:id`: Instantly cancels a background processing job, freeing up system resources.
   - `POST /api/v1/clips/:id/next`: Triggers on-demand generation of the next clip from the remaining scored transcript chunks.

2. **Smart Processing Pipeline**
   - **Transcript Download**: Fetches auto-generated subtitles directly from YouTube.
   - **Heuristic Scoring**: Splits the transcript into 5-minute chunks and scores them based on punctuation (exclamation/question marks) and emotional keywords (e.g., *wow, crazy, shocking*).
   - **LLM Timestamp Extraction**: Sends the highest-scoring chunk to Ollama, intelligently extracting 30-90 seconds of the most engaging moments.
   - **Video Slicing & Cropping**: Downloads the video via yt-dlp, trims it based on the LLM's timestamps, and reformats the aspect ratio to 9:16 using FFmpeg.
   - **On-Demand Generation**: Only 1 clip is generated initially. Remaining scored chunks are stored in-memory for subsequent "Generate More" requests, conserving CPU and memory.

3. **Concurrency Limiter (Semaphore)**
   - A global buffered channel (`processingSemaphore`, capacity: 1) ensures only one heavy process (LLM + FFmpeg) runs at a time. This prevents resource starvation when multiple clients submit jobs simultaneously.

4. **Smart Deduplication Caching**
   - Before creating a new job, the handler checks the `JobStore` for a previously completed job with the same `OriginalURL` and `LayoutMode`. If found, the cached result is returned instantly (HTTP 200), avoiding all redundant processing.

5. **Dynamic FFmpeg Arguments**
   - The backend detects the operating system at runtime via `runtime.GOOS`:
     - **macOS (darwin)**: Uses `h264_videotoolbox` hardware acceleration for fast encoding on Apple Silicon.
     - **Linux (VPS)**: Falls back to `libx264` software encoding with `-preset veryfast` to avoid CPU timeout on low-spec servers.

6. **Master Video Caching & Auto Cleanup Routine**
   - The master video downloaded via `yt-dlp` is retained in disk and its path stored in the job state, allowing "Generate More" requests to instantly reuse the file without redownloading.
   - A background goroutine runs periodically to purge expired jobs (TTL: 2 hours), automatically deleting temp files, output clips, and in-memory state to prevent disk bloat and memory leaks.

## 🐛 Critical Issues Resolved

During development, several edge cases and bugs were addressed to ensure the system remains robust:

1. **LLM Timestamp Hallucinations**
   - *Problem*: The LLM would occasionally invent timestamps (e.g., 10 hours) because it lacked a strict time reference.
   - *Solution*: Modified the VTT parser to inject inline timestamps (`[HH:MM:SS]`) directly into the transcript text. The prompt was also updated to strictly limit the LLM to only select times explicitly present in the text.

2. **Apple QuickTime Compatibility**
   - *Problem*: Videos generated by FFmpeg couldn't be played natively on macOS/iOS via QuickTime.
   - *Solution*: Forced FFmpeg to use Apple's standard pixel format (`-pix_fmt yuv420p`) and ensured video dimensions are always even numbers using a specialized crop filter.

3. **yt-dlp "HTTP 429: Too Many Requests" Errors**
   - *Problem*: YouTube rate-limited the application when attempting to download multi-language subtitles rapidly.
   - *Solution*: Implemented "Partial Failure Tolerance". If the English subtitles fail to download but the Indonesian ones succeed, the system continues processing instead of aborting the job.

4. **Flexible Configuration**
   - Migrated from hardcoded configurations to a `.env`-based system using `godotenv`. Users can now easily adjust the `PORT`, `OLLAMA_MODEL`, and output directory without recompiling the code.

5. **Resource Leak Prevention (Context Cancellation)**
   - *Problem*: If a user canceled the process on the frontend, the backend would continue running FFmpeg, wasting CPU cycles.
   - *Solution*: Injected `context.Context` and its `CancelFunc` into `exec.CommandContext`. Now, when the `DELETE` API is called, yt-dlp and FFmpeg are programmatically terminated (`SIGKILL`) instantly.

6. **Unknown Encoder on Linux VPS**
   - *Problem*: Deploying to a Linux VPS caused `Unknown encoder 'h264_videotoolbox'` errors because VideoToolbox is macOS-only.
   - *Solution*: Implemented OS-adaptive FFmpeg arguments using `runtime.GOOS` to automatically select the appropriate encoder.
